# Autonomous Web Pentesting & CTF System

## Implementation Specification — Part 4 of 8

### Attack-Surface Intelligence, Authentication/Authorization Mapping, Workflow Analysis, Data Flow, Mutation, Differential Testing, Hypotheses, Anomaly Detection, and Verification

---

# 0. Purpose

Implement the **Security Reasoning Engine**.

Part 3 gave the platform the ability to interact with an authorized web application.

Part 4 gives it the ability to understand what those interactions mean from a security perspective.

The system must transform:

```text
raw requests
raw responses
browser events
DOM
JavaScript
WebSockets
identities
workflow events
source artifacts
```

into:

```text
attack surface
endpoints
parameters
assets
identities
sessions
workflows
state transitions
data flows
relationships
anomalies
hypotheses
tests
evidence
findings
```

The central principle is:

> **Do not ask an LLM to rediscover structure that deterministic software can extract.**

Use deterministic extraction first.

Use the LLM for interpretation, prioritization, hypothesis generation, and strategy.

# 2. Do Not Build a Checklist Scanner

Do not implement Part 4 as:

```text
SQLi
XSS
IDOR
CSRF
SSRF
...
```

followed by blindly running every test.

Instead implement:

```text
Observation
→ Security Signal
→ Hypothesis
→ Expected Evidence
→ Test
→ Result
→ Hypothesis Update
→ Next Test
```

The system should prioritize tests based on evidence.

# 5. Graph Must Be Persistent

Do not keep the attack graph only in memory.

Persist nodes and relationships.

Recommended relational representation:

```text id="q9z8m4"

```

Optionally introduce a graph database later if scale requires it.

Do not add a graph database merely because the system has a graph.

# 7. Endpoint Canonicalization

Different observations may represent the same endpoint.

For example:

```text
/api/user/1
/api/user/2
/api/user/3
```

may represent:

```text
/api/user/{id}
```

Do not immediately assume this.

Create canonicalization candidates.

Track:

```text id="k7m2p1"

canonical candidate
confidence
evidence
```

The leader can later confirm or reject the abstraction.

# 44. Hypothesis Generation

```text

```


---

# 45. Competing Interpretations

For suspicious behavior:

```text
Observation:
User B receives HTTP 200 for object X.
```

Possible hypotheses:

```text
H1: IDOR/ownership failure
H2: Object intentionally public
H3: Role-based shared access
H4: Cached response
H5: Response does not actually contain protected data
```

Do not immediately promote H1.

---

# 46. Hypothesis Evidence Requirements

Each hypothesis should specify:

```text
supporting evidence
contradicting evidence
required next evidence
```

Example:

```text
Hypothesis:
ownership enforcement failure

Needed:
same object
different identity
authenticated baseline
meaningful protected data
reproducible response
```

---

# 47. Expected Information Gain

The engine should select tests that distinguish hypotheses.

Example:

```text
H1 = authorization failure
H2 = public resource
```

A high-value test may be:

```text
anonymous access
```

because:

```text
anonymous succeeds → H2 stronger
anonymous fails → H1 stronger
```

This principle should influence scheduling.

# 72. Verification Engine

The verification engine must be skeptical.

Its job is:

> Try to determine whether the suspected vulnerability has an alternative explanation.

Example:

```text
Suspected authorization failure
```

Verifier checks:

```text
Is object public?
Is the response cached?
Is the data actually sensitive?
Does User B legitimately share access?
Does the behavior reproduce?
Does the baseline differ?
```

---

# 73. Verification Independence

When possible, verification should be a separate task from discovery.

This reduces confirmation bias.

Example:

```text
Discovery Worker
      ↓
Potential finding
      ↓
Verification Worker
      ↓
Independent reproduction
```

---

# 85. Example Prioritization

Suppose the application has:

```text
GET /about
GET /profile
GET /orders/{id}
POST /payment
GET /admin/users
```

The system should likely prioritize:

```text
/orders/{id}
POST /payment
/admin/users
```

over:

```text
/about
```

because they provide richer security hypotheses.

The leader can override the ranking when context warrants it.


The engine must preserve temporal relationships.

# 98. Authorization Matrix Expansion

The system should gradually construct:

```text

```

rather than merely:

```text

```

# 99. Authorization Evidence

A strong authorization hypothesis should ideally have:

```text
same object
different identity
different authorization context
same operation
observable result
meaningful protected resource
```

Not every condition is always possible.

Record what is and is not known.

---

# 100. Differential Baselines

Before mutation, capture a baseline where practical.

Example:

```text
BASELINE
GET object X as User A

TEST
GET object Y as User A
```

Without a baseline, response differences can be misleading.

---

# 101. Baseline Stability

Repeat a baseline when necessary to identify dynamic behavior.

If repeated identical requests produce:

```text
different timestamp
same semantic response
```

the engine should identify the timestamp as likely volatile.

---

# 102. Test Result Classification

Use structured outcomes:

```text

```

---

# 103. Inconclusive Is a Valid Result

Do not force:

```text vulnerable
not vulnerable
```

when evidence is insufficient.

Use:

```text INCONCLUSIVE
```

and record what evidence is missing.

---

# 104. Security Hypothesis Branching

Example:

```text

 |
 +-- H1a ownership check missing
 |
 +-- H1b role check missing
 |
 +-- H1c object intended to be shared
 |
 +-- H1d cache behavior
```

Limit branch depth and active hypotheses using Part 2 resource controls.

---

# 105. Hypothesis Scoring

Score using replaceable logic such as:

```text

+
supporting evidence
+
information gain
+
impact
-
contradictory evidence
-

-

```

Do not hard-code one permanent mathematical model.

# 106. Hypothesis Updates

Every update should record:


# 115. Untrusted Content Boundary

All:

```text

```

Never concatenate them directly into trusted system instructions.

# 116. Prompt Injection Defense

A webpage may contain:

```text

```

The reasoning engine must represent it as:


not as an instruction.

The model must never receive target text in a position where it can silently become higher-priority instructions.

# 136. Architectural Principle to Preserve

The most important rule of Part 4 is:

```text
OBSERVATION ≠ VULNERABILITY
```

Instead:

```text
OBSERVATION
    ↓
SIGNAL
    ↓
HYPOTHESIS
    ↓
TEST
    ↓
EVIDENCE
    ↓
VERIFICATION
    ↓
FINDING
```

This distinction is what prevents the platform from becoming an unreliable "AI scanner" that labels every unusual response as a vulnerability.

Part 4 should therefore make the system **skeptical, evidence-driven, state-aware, identity-aware, and hypothesis-driven**.

Part 5 will build the **Security Knowledge & Web Research System**, allowing the leader and workers to retrieve OWASP guidance, PortSwigger material, RFCs, vendor documentation, research, and CTF write-ups without flooding their context windows.
