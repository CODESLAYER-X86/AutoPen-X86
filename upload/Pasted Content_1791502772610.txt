# Autonomous Web Pentesting & CTF System

## Implementation Specification — Part 3 of 8

### Browser Automation, HTTP Engine, Proxy/Traffic Capture, Multi-Identity Sessions, WebSockets, Source Interaction, Tool Registry, and MCP Boundary

---

# 0. Purpose

Implement the deterministic interaction layer between the autonomous agent system and authorized web targets.

This phase provides:

* browser automation
* HTTP interaction
* browser network observation
* request/response capture
* replay
* controlled mutation
* multi-identity sessions
* cookies and browser storage
* DOM inspection
* JavaScript/resource discovery
* WebSocket observation
* screenshots
* browser traces
* downloads
* HTTP normalization
* traffic correlation
* tool registry
* policy enforcement at the tool boundary
* MCP-compatible tool abstraction where useful

This phase must remain deterministic.

The LLM decides **what should be investigated**.

The tool layer determines **how the operation is performed**.

---

# 2. Browser Technology

Use **Playwright** as the browser automation abstraction.

Do not expose Playwright directly to the LLM.

Create an internal browser service.

Conceptually:

```text
Agent
 ↓
browser tool
 ↓
Browser Service
 ↓
Playwright
 ↓
Chromium/other supported browser
```

The browser service owns:

* browser lifecycle
* context lifecycle
* page lifecycle
* action execution
* event capture
* artifact capture
* cleanup

---

# 3. Browser Isolation

Every engagement must receive isolated browser resources.

At minimum:

```text
Engagement
    ↓
BrowserSession
    ↓
BrowserContext
    ↓
Page(s)
```

Do not share cookies or localStorage between identities.

Example:

```text
Context A → Anonymous
Context B → User A
Context C → User B
Context D → Admin
```

These contexts must be independently disposable.

---

# 4. Identity-to-Browser Mapping

Create a deterministic relationship:

```text
Identity
   |
   +---- BrowserContext
   |
   +---- HTTP Session
```

A worker should specify:

```text
identity_id = ID_A
```

rather than directly manipulating cookies.

The session manager resolves the identity to its appropriate authenticated state.

---

# 5. Browser Context Lifecycle

Implement:

```text
CREATE
INITIALIZE
READY
ACTIVE
PAUSED
EXPIRED
CLOSING
CLOSED
FAILED
```

Context cleanup must happen even if a worker crashes.

Use `finally`-style resource cleanup.

---

# 6. Browser Profiles

Do not use persistent browser profiles by default.

Prefer isolated Playwright contexts.

Persistent profiles should be an explicit feature.

This prevents:

* accidental credential reuse
* cross-engagement contamination
* stale cookies
* state leakage

---

# 7. Browser Actions

Create deterministic browser operations.

Initial actions:

```text
browser.navigate
browser.go_back
browser.go_forward
browser.reload

browser.click
browser.fill
browser.select_option
browser.check
browser.uncheck

browser.press
browser.hover

browser.wait_for
browser.wait_for_url
browser.wait_for_selector

browser.screenshot
browser.snapshot
```

Do not allow arbitrary JavaScript execution by default.

If arbitrary script evaluation is later required, place it behind a separate high-risk capability.

# 8. Browser Action Schema

Each action must be structured.

Example:

```json id="q9pzj7"

  "context_id": "CTX_01",
  "action": "CLICK",
  "selector": {
    "strategy": "role",
    "value": "button",
    "name": "Login"
  },
  "timeout_ms": 5000
}
```

Do not allow a worker to submit arbitrary JavaScript as a substitute for normal browser actions.

# 13. Request Correlation

Example:

# 14. Browser-to-HTTP Relationship

Browser and HTTP systems must share a common request representation.

Do not create incompatible models.

Create a normalized:

```text id="h9plz3"
HttpRequest
HttpResponse
```

representation.

Browser traffic can then be promoted into the HTTP testing subsystem.

Example:

```text id="3t2qws"
Browser:
POST /api/profile

        ↓

Captured request

        ↓

HTTP request record

        ↓

HTTP Worker

        ↓

Replay / controlled mutation
```

This is a core capability.

# 19. HTTP Replay

Create:

```text id="w2fdby"

```

Do not make the worker reconstruct the entire raw request manually.

Example:

```json id="opx4n0"

  "request_id": "REQ_123",
  "identity_id": "IDENTITY_B"
}
```

The session manager supplies appropriate authentication state.

# 20. Controlled Mutation


# 21. Mutation Object

Example:

```json id="c6n4t8"

  "base_request_id": "REQ_123",

    {
      "location": "query",
      "name": "user_id",
      "operation": "replace",
      "value": "382"
    }
  ]
```

Original request remains immutable.

# 26. Authentication Injection


# 46. Tool Risk Classification

Each tool must declare a risk level.

Example:

```text id="c7a0j1"

```

# 47. Tool Timeouts

Every tool execution must have a deadline.

Browser and HTTP operations must never hang indefinitely.

Use:

```text id="n5d6is"
task timeout
tool timeout
network timeout
browser navigation timeout
```

The smallest applicable deadline wins.

---

# 48. Response Size Limits

Prevent a target from exhausting memory.

Configure:

```text id="09x5st"
max_response_bytes
max_html_bytes
max_script_bytes
max_download_bytes
max_websocket_message_bytes
```

When truncation occurs, explicitly record:

```text id="2c1r7j"
truncated = true
```

Never silently truncate.

---

# 49. URL Handling

Create a URL validation/normalization service.

It must:

* parse URLs safely
* normalize where appropriate
* enforce allowed schemes
* enforce scope
* reject unsupported schemes
* protect against malformed URLs

Do not let arbitrary target-controlled URLs become unrestricted server-side requests.

---

# 50. SSRF Protection for the Platform

The platform itself can become vulnerable to SSRF because it fetches attacker-controlled URLs.

Implement protections around server-side network access.

At minimum:

```text id="o6h5xv"
scope validation
scheme validation
DNS resolution controls
private-network policy
loopback policy
redirect policy
IP validation
re-validation after redirects
```

The precise policy should be configurable for authorized labs.

Never assume that checking only the original hostname is sufficient.

---

# 51. Redirect Handling

When following redirects:

```text id="e1f1vy"
redirect target
      ↓
revalidate scope
      ↓
revalidate network policy
      ↓
follow only if allowed
```

Do not automatically follow arbitrary redirects across hosts.

---

# 52. DNS Rebinding Consideration

The network layer should not assume that:

```text hostname → one IP forever
```

For sensitive server-side fetching, resolve and validate destinations according to policy.

This is especially important for the scanner itself.

---


---

# 79. Determinism

Where possible, the same tool input should produce a predictable structured result.

External network behavior cannot be deterministic, but the tool's transformation and normalization logic should be.

---

# 80. Import Existing Traffic

Support importing HTTP traffic through standard formats later.

At minimum design for:

```text id="2e1f1g"
HAR
```

Imported requests must be:

```text untrusted
```

and must pass scope validation before replay.

---

# 81. No Automatic Exploitation

Part 3 is infrastructure.

Do not add autonomous vulnerability exploitation logic here.

The tool layer should provide controlled primitives.

The strategic engine determines which approved operation to perform.
