     1→# Autonomous Web Pentesting & CTF System
     2→
     3→## Implementation Specification — Part 3 of 8
     4→
     5→### Browser Automation, HTTP Engine, Proxy/Traffic Capture, Multi-Identity Sessions, WebSockets, Source Interaction, Tool Registry, and MCP Boundary
     6→
     7→---
     8→
     9→# 0. Purpose
    10→
    11→Implement the deterministic interaction layer between the autonomous agent system and authorized web targets.
    12→
    13→This phase provides:
    14→
    15→* browser automation
    16→* HTTP interaction
    17→* browser network observation
    18→* request/response capture
    19→* replay
    20→* controlled mutation
    21→* multi-identity sessions
    22→* cookies and browser storage
    23→* DOM inspection
    24→* JavaScript/resource discovery
    25→* WebSocket observation
    26→* screenshots
    27→* browser traces
    28→* downloads
    29→* HTTP normalization
    30→* traffic correlation
    31→* tool registry
    32→* policy enforcement at the tool boundary
    33→* MCP-compatible tool abstraction where useful
    34→
    35→This phase must remain deterministic.
    36→
    37→The LLM decides **what should be investigated**.
    38→
    39→The tool layer determines **how the operation is performed**.
    40→
    41→---
    42→
    43→# 1. Fundamental Architecture
    44→
    45→Implement:
    46→
    47→```text
    48→                         ORCHESTRATOR
    49→                              |
    50→                              v
    51→                         TASK SCHEDULER
    52→                              |
    53→                              v
    54→                        WORKER RUNTIME
    55→                              |
    56→                 +------------+------------+
    57→                 |            |            |
    58→                 v            v            v
    59→            HTTP WORKER  BROWSER WORKER  SOURCE WORKER
    60→                 |            |
    61→                 v            v
    62→             HTTP API     PLAYWRIGHT
    63→                 |            |
    64→                 |       Browser Context
    65→                 |            |
    66→                 +-----+------+ 
    67→                       |
    68→                       v
    69→                 TRAFFIC LAYER
    70→                       |
    71→             +---------+---------+
    72→             |                   |
    73→             v                   v
    74→        Request Store       Observation
    75→                             Pipeline
    76→             |                   |
    77→             +---------+---------+
    78→                       |
    79→                       v
    80→                  EVIDENCE STORE
    81→```
    82→
    83→---
    84→
    85→# 2. Browser Technology
    86→
    87→Use **Playwright** as the browser automation abstraction.
    88→
    89→Do not expose Playwright directly to the LLM.
    90→
    91→Create an internal browser service.
    92→
    93→Conceptually:
    94→
    95→```text
    96→Agent
    97→ ↓
    98→browser tool
    99→ ↓
   100→Browser Service
   101→ ↓
   102→Playwright
   103→ ↓
   104→Chromium/other supported browser
   105→```
   106→
   107→The browser service owns:
   108→
   109→* browser lifecycle
   110→* context lifecycle
   111→* page lifecycle
   112→* action execution
   113→* event capture
   114→* artifact capture
   115→* cleanup
   116→
   117→---
   118→
   119→# 3. Browser Isolation
   120→
   121→Every engagement must receive isolated browser resources.
   122→
   123→At minimum:
   124→
   125→```text
   126→Engagement
   127→    ↓
   128→BrowserSession
   129→    ↓
   130→BrowserContext
   131→    ↓
   132→Page(s)
   133→```
   134→
   135→Do not share cookies or localStorage between identities.
   136→
   137→Example:
   138→
   139→```text
   140→Context A → Anonymous
   141→Context B → User A
   142→Context C → User B
   143→Context D → Admin
   144→```
   145→
   146→These contexts must be independently disposable.
   147→
   148→---
   149→
   150→# 4. Identity-to-Browser Mapping
   151→
   152→Create a deterministic relationship:
   153→
   154→```text
   155→Identity
   156→   |
   157→   +---- BrowserContext
   158→   |
   159→   +---- HTTP Session
   160→```
   161→
   162→A worker should specify:
   163→
   164→```text
   165→identity_id = ID_A
   166→```
   167→
   168→rather than directly manipulating cookies.
   169→
   170→The session manager resolves the identity to its appropriate authenticated state.
   171→
   172→---
   173→
   174→# 5. Browser Context Lifecycle
   175→
   176→Implement:
   177→
   178→```text
   179→CREATE
   180→INITIALIZE
   181→READY
   182→ACTIVE
   183→PAUSED
   184→EXPIRED
   185→CLOSING
   186→CLOSED
   187→FAILED
   188→```
   189→
   190→Context cleanup must happen even if a worker crashes.
   191→
   192→Use `finally`-style resource cleanup.
   193→
   194→---
   195→
   196→# 6. Browser Profiles
   197→
   198→Do not use persistent browser profiles by default.
   199→
   200→Prefer isolated Playwright contexts.
   201→
   202→Persistent profiles should be an explicit feature.
   203→
   204→This prevents:
   205→
   206→* accidental credential reuse
   207→* cross-engagement contamination
   208→* stale cookies
   209→* state leakage
   210→
   211→---
   212→
   213→# 7. Browser Actions
   214→
   215→Create deterministic browser operations.
   216→
   217→Initial actions:
   218→
   219→```text
   220→browser.navigate
   221→browser.go_back
   222→browser.go_forward
   223→browser.reload
   224→
   225→browser.click
   226→browser.fill
   227→browser.select_option
   228→browser.check
   229→browser.uncheck
   230→
   231→browser.press
   232→browser.hover
   233→
   234→browser.wait_for
   235→browser.wait_for_url
   236→browser.wait_for_selector
   237→
   238→browser.screenshot
   239→browser.snapshot
   240→```
   241→
   242→Do not allow arbitrary JavaScript execution by default.
   243→
   244→If arbitrary script evaluation is later required, place it behind a separate high-risk capability.
   245→

   248→# 8. Browser Action Schema
   249→
   250→Each action must be structured.
   251→
   252→Example:
   253→
   254→```json id="q9pzj7"
   255→{
   256→  "context_id": "CTX_01",
   257→  "action": "CLICK",
   258→  "selector": {
   259→    "strategy": "role",
   260→    "value": "button",
   261→    "name": "Login"
   262→  },
   263→  "timeout_ms": 5000
   264→}
   265→```
   266→
   267→Do not allow a worker to submit arbitrary JavaScript as a substitute for normal browser actions.
   268→

   271→# 9. Selector Strategy
   272→
   273→Support deterministic selector strategies:
   274→
   275→```text id="plq1fr"
   276→role
   277→text
   278→label
   279→placeholder
   280→css
   281→xpath
   282→test_id
   283→```
   284→
   285→Prefer stable semantic selectors.
   286→
   287→The browser service should normalize selector errors.

   390→# 13. Request Correlation
   391→
   392→Every browser request must receive a unique internal ID.
   393→
   394→Example:
   395→
   396→```text id="oy5c4r"
   397→Browser Event
   398→    |
   399→    v
   400→REQ_BROWSER_001
   401→    |
   402→    +── request
   403→    +── response
   404→    +── page
   405→    +── context
   406→    +── identity
   407→    +── task
   408→    +── evidence
   409→```
   410→
   411→This lets the system trace:
   412→
   413→```text
   414→user clicked button
   415→→ JavaScript executed
   416→→ API request occurred
   417→→ response returned
   418→→ DOM changed
   419→```

   423→# 14. Browser-to-HTTP Relationship
   424→
   425→Browser and HTTP systems must share a common request representation.
   426→
   427→Do not create incompatible models.
   428→
   429→Create a normalized:
   430→
   431→```text id="h9plz3"
   432→HttpRequest
   433→HttpResponse
   434→```
   435→
   436→representation.
   437→
   438→Browser traffic can then be promoted into the HTTP testing subsystem.
   439→
   440→Example:
   441→
   442→```text id="3t2qws"
   443→Browser:
   444→POST /api/profile
   445→
   446→        ↓
   447→
   448→Captured request
   449→
   450→        ↓
   451→
   452→HTTP request record
   453→
   454→        ↓
   455→
   456→HTTP Worker
   457→
   458→        ↓
   459→
   460→Replay / controlled mutation
   461→```
   462→
   463→This is a core capability.
   464→

   467→# 15. HTTP Engine
   468→
   469→Implement an independent HTTP client service.
   470→
   471→It should support:
   472→
   473→```text id="g2ct9a"
   474→GET
   475→POST
   476→PUT
   477→PATCH
   478→DELETE
   479→HEAD
   480→OPTIONS
   481→```
   482→
   483→Potentially other methods later.
   484→
   485→Use a mature HTTP implementation.
   486→
   487→Do not implement HTTP from raw TCP unless a specialized feature later requires it.
   488→

   560→
   561→Normalize requests before comparison.
   562→

   564→
   565→* header ordering
   566→* URL normalization
   567→* query ordering
   568→* JSON key ordering where appropriate
   569→* whitespace where appropriate
   570→
   571→Do not destroy semantically meaningful differences.
   572→
   573→Store both:
   574→
   575→```text id="1o5wfd"
   576→raw
   577→normalized

   582→# 19. HTTP Replay
   583→
   584→Create:
   585→
   586→```text id="w2fdby"
   587→http.replay
   588→```
   589→
   590→Input should reference an existing request whenever possible.
   591→
   592→Do not make the worker reconstruct the entire raw request manually.
   593→
   594→Example:
   595→
   596→```json id="opx4n0"
   597→{
   598→  "request_id": "REQ_123",
   599→  "identity_id": "IDENTITY_B"
   600→}
   601→```
   602→
   603→The session manager supplies appropriate authentication state.

   608→
   609→Create:
   610→
   611→```text id="4n7uj1"
   612→http.mutate
   613→```
   614→
   615→Mutation must be structured.
   616→
   617→Examples:
   618→
   619→```text id="n0c7kg"
   620→change_query_parameter
   621→change_json_field
   622→change_header
   623→change_cookie_reference
   624→change_path_segment
   625→change_method
   626→change_form_field
   627→```
   628→
   629→Do not require the LLM to manually edit raw HTTP strings.
   630→
   631→---
   632→
   633→# 21. Mutation Object
   634→
   635→Example:
   636→
   637→```json id="c6n4t8"
   638→{
   639→  "base_request_id": "REQ_123",
   640→  "mutations": [
   641→    {
   642→      "location": "query",
   643→      "name": "user_id",
   644→      "operation": "replace",
   645→      "value": "382"
   646→    }
   647→  ]
   648→}
   649→```
   650→
   651→The mutation engine creates a new request.
   652→
   653→Original request remains immutable.
   654→
   655→---
   656→
   657→# 22. Mutation Safety
   658→
   659→Mutation must enforce:
   660→
   661→```text id="j5hy0x"
   662→scope
   663→request size
   664→allowed methods
   665→resource limits
   666→identity permissions
   667→engagement policy
   668→```
   669→
   670→A mutation cannot change the destination to an out-of-scope target.

   739→# 26. Authentication Injection
   740→
   741→When an HTTP request is executed as:
   742→
   743→```text
   744→identity_id = USER_A
   745→```

   748→

   753→# 27. Session Expiration
   754→
   755→Detect:
   756→
   757→```text id="s9p2g8"
   758→expired session
   759→invalid token
   760→logout
   761→authentication redirect
   762→401
   763→403

   765→```
